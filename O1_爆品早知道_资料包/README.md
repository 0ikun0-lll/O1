# O1 · 爆品早知道 —— 新品冷启动动销潜力预测

> 本赛题使用**模拟真实业务形态、已做脱敏**的数据：商品属性、类目、店铺画像与销量档位参照真实上架记录构造；商品 / 店铺 / 供应商 / 类目 ID 全部重编码且**已打乱编号顺序**，时间轴整体平移为**上架批次**，评分与规模类指标一律降级为 band 或相对指数，**销量绝对值不下发**，**不含图像数据**。
>
> ⚠️ **数据使用边界**：`attr_vals` 为商家填写的**属性原文**（可能夹杂营销话术、尺码提示等非结构化文本），已保留原始形态用于文本建模；其中不含店铺 / 商品可识别编号，但**仅限本次比赛使用**。请勿对外传播、二次分发或用于赛题之外的任何用途。组织者保留对明显不当内容做后续清理的权利，清理不影响评分口径。
>
> **本包只含公开测试集。隐藏测试集（特征与标签）由组织者持有，不随包下发**——终评通过代码提交在隐藏集上运行，见 §2.1。
>
> **口径说明**：店铺侧 `score_band / onsale_band / follow_band` 与 `is_*_shop`、`shop_level`、`supplier_layer`、`shop_main_cate` 一律取**商品上架当日**的店铺快照，不含上架后销量或评价；数据中不含 `group_band`。

## 0. 读之前必须知道的四件事

1. **编号没有任何含义**：`item_id` / `shop_id` / `supplier_id` / `cate_code` 都是随机重编码。按编号大小排序、按文件行号排序，都和档位无关——**不要试图从编号或行序里找信号**，那只是噪音（我们也做过校验：编号与档位的相关系数 ≈ 0）。
2. **时间是"上架批次"不是日历月**：`listing_batch = B01…B07` 是按真实上架时间先后切出的 7 个批次（B01–B06 各覆盖**真实 2 个自然日**的上架量，B07 覆盖 3 个），**不是自然月，没有季节性含义**。B01 最早，B07 最晚。
3. **时间快照的截止点**：`shop_hist_monthly` 与 `category_trend.demand_index` 的行标 `batch = m` 表示"**进入批次 m 之前**的状态"，所以对 `listing_batch = Bk` 的商品只能取 `batch ≤ Bk` 的行。`category_trend.demand_index` 已按此滞后：`batch = Bk` 的值由 **Bk-1 批次整批结算后的动销**计算，**不含本批次（也就是不含被预测商品自己）的销量**。**例外**：`category_trend.supply_count` 表示 `batch = m` 这一批次的供给压力（业务池口径，含本批次商品，不含任何标签），作为**同批次供给信息**使用，不是"批次前快照"。
   - **终评沙箱细节**：`shop_hist_monthly` 的 `B07` 行与 `B06` 行完全相同——店铺历史只结算到训练窗口 `B05`，公开集（B06）的动销结果**不进入 `shop_hist_monthly`**（`category_trend` 的 B07 行有自己的口径，见 §7 FAQ）。预测隐藏批（B07）时，店铺历史最多只到 B05 状态，这是刻意设计，不是缺行。
   - **band 类字段的取样时点**：`score_band / onsale_band / follow_band` 按**该商品自己的上架日**取当日店铺快照（同一批次内不同上架日会取到不同日的快照），连同 `is_*_shop`、`shop_level`、`supplier_layer`、`shop_main_cate` 一起，**均不含上架后的销量/评价反馈**。个别字段在一个店铺/商品上恒定，是因为脱敏后只保留 band，不代表时间序列。
   - **数据中不含 `group_band`**：同款组表的日分区里，上架当日的新品基本还没入组（抽样上架新品 300 件，上架当日分区仅命中极少；即使追到后续日期也只有约一半曾入组），无法给出"上架当日"口径。该字段与档位秩相关仅 0.057，`is_similar` 在本批恒为 0，同款信息在本题本来就不可用——数据字典不含该列，**不要按其他资料去找它**。
4. **销量绝对值不存在**：档位 `tier` 与所有规模指标都是 band / 相对指数，无法反推销量。

## 1. 场景

某跨境时尚平台每天有大量新品上架。运营必须在**上架当天**决定：

- **上新优先级**：哪些新品值得先给流量（排序问题）；
- **放行 / 驳回**：潜力过低的新品退回商家优化，或直接放行（二元决策，错判有不对称代价：错杀爆品约 3 倍贵于放过平庸品）。

可用的信息只有**上架时点已存在**的东西：商品属性组合、类目、价格、店铺画像与**严格截止的历史快照**、类目需求趋势。
**上架后的任何数据（销量、审核流水、机审分）一律不可用——数据包里也根本没有。**

动销分档（按上架后短窗销量的**绝对阈值**分档，阈值组织者持有、固定不变）：
**S**（爆品，约占 5%）/ **A**（15%）/ **B**（30%）/ **C**（30%）/ **D**（20%）。

### 四个真实世界的考点（都是考点，不是缺陷）

1. **新店冷启动**：`register_batch = B06 / B07` 的店铺分别有 **386 / 315 家**，训练期零历史；公开测试集 **22.0%**（660 / 3,000）、隐藏测试集 **22.6%**（677 / 3,000）的商品来自训练集里**一条记录都没有**的店铺。
2. **店铺历史稀薄**：`shop.csv` 共 **5,528 家店**，其中 **4,827 家**在训练集（20,000 品）里出现过；其余 701 家仅出现在测试批次（386 家公开集专属 + 315 家隐藏集专属，三批并集恰为 5,528）。**73.6% 的「店铺 × 批次」快照里 `cum_sku ≤ 2`**（中位数 1，均值 2.1）——"大概率没有先验"才是常态。
3. **缺失本身是信号**：`price` 缺失 **54.6%**（新品无站内比价，且与 `has_price_ref=0` 完全等价）；`n_attr_rows / n_attr_types = -1` 占 **35.1%**（与 `attr_vals` 为空完全重合）；`is_similar`、`is_kol_shop` 在本批数据中恒为 0。
4. **合作模式与属性完整度强相关（真实业务形态，非泄漏）**：`fulfillment_mode = 全托管` 的 14,932 品**全部**有属性（`n_attr_rows != -1`）；`半托管`（4,224）与 `自运营`（3,844）**全部**无属性（`n_attr_rows = -1`），两类共 8,068 行严格一一对应。这是平台合作模式决定商家是否填写属性，真实业务里就长这样。**注意**：仅凭 `fulfillment_mode` 单字段做决策（全托管放行、其余驳回）的**原始决策分**约 **0.51–0.54**；这条规则被定义为"地板"，记 **0 分**——决策侧必须在地板之上做出增量，才说明用上了商品自身信息（见 §5、§6）。

> 口径说明：以上比例与计数均按本包 `train.csv` + `test_public.csv` 共 23,000 品统计。

### 2.2 本地如何模拟终评（务必按下面三步）

**不要**手工把 `test_public.csv` 改名成 `test.csv` 就直接跑——那样训练集仍是完整 `train.csv`（含验证批标签），分数会虚高。正确做法是用随包的 `make_local_datadir.py` 一次性拼出与沙箱同构的目录：

```bash
# ① 切分并组装 data-dir（默认验证批 B05；--val-batch B04 则验证 B04–B05）
python3 make_local_datadir.py --src . --out /tmp/o1_val --mode val --val-batch B05

# ② predict.py 只读 --data-dir（与终评同一接口）
python3 predict.py --data-dir /tmp/o1_val --out /tmp/val_pred.csv

# ③ 用独立真值打分（真值在 data-dir 之外）
python3 evaluate.py --pred /tmp/val_pred.csv --truth /tmp/o1_val_truth.csv \
    --items /tmp/o1_val/test.csv --train /tmp/o1_val/train.csv
```

脚本会自动完成：按批次切 `train.csv`；验证批特征写成 `test.csv`（去掉 `tier`）；`baseline_scores.csv` 只保留训练集行；`shop_hist_monthly.csv` / `category_trend.csv` 截到验证批为止；真值单独写到 `/tmp/o1_val_truth.csv`，**不要拷进 data-dir 或代码包**。

需要模拟"公开集预测"时用 `--mode public`（`test.csv = test_public.csv`、`train.csv = 完整训练集`），但公开集**没有标签**，只能跑通链路、不能本地打分。`--val-batch` 是**起点（含）**。

> 提醒：`--val-batch B04` 会同时留出 B04、B05，但 B05 批的店铺历史快照仍包含 B04 的真实结果，B04–B05 两批的本地分数会略高估店铺历史特征的收益，只适合粗略对比；选型与汇报请以默认的 `--val-batch B05` 为准（训练 B01–B04，验证 B05，验证集店铺历史只含 B01–B04 的结果）。

> **与终评沙箱的三点差异**：① 本包 `category_trend` 只到 B06，终评沙箱会多出 B07 行——代码里请**按 `batch <= 当前批次` 过滤**，不要假设行数/列数固定；② 沙箱 `shop_hist_monthly` 的 B07 行等于 B06 行（只结算到训练窗口 B05），本地已按同样口径截断；③ 真值文件只在本地存在，`predict.py` 不得读取，也不要把验证批真值或由它衍生的答案映射带进代码包。

| `val_truth.csv` | 同上 | 验证批的真值（`item_id,tier,group`），**只用来算分，绝不能进模型** |

⚠️ 这 5 个文件每次重跑都会**覆盖同名文件**（`evaluate.py --make-val` 会重写前三个，`baseline.py` 会重写后两个）；生成的 `train_sub.csv` 等一律留在当前目录，**不要**把它们拷进提交的代码包里。

## 4. 任务

对 `test_public.csv`（公开榜）与隐藏集（终评）输出：
`decision ∈ {放行, 驳回}` 与排序分 `score`（越大越优先上新）。

提交文件只认三列：`item_id,score,decision`。字段与评分项的对应关系：

| 输出字段 | 进入哪个评分项 | 说明 |
|---|---|---|
| `score` | **NDCG 部分（客观分的 60%）** | 组内排序，越大越优先；同分按 `item_id` 升序兜底 |
| `decision` | **决策得分（客观分的 40%，超出单字段地板的增量）** | `放行` / `驳回`；与 `score` 独立计分 |
| `pred_tier` | — | **不参与评分**，不要输出；提交只认上述三列 |

## 5. 评测方式

**客观分 = 0.6 × NDCG 部分 + 0.4 × 决策得分**，公开榜与隐藏榜独立计算：

```
NDCG 部分 = 0.8 × 分层 NDCG（随机归一化） + 0.2 × 冷启动子分
客观分    = 0.6 × NDCG 部分 + 0.4 × 决策得分
两榜加权客观总分 = 0.3 × 公开榜客观分 + 0.7 × 隐藏榜客观分
```

> **术语说明**：上式的 `0.3 / 0.7` 加权结果只是**客观评分部分的汇总**，不是赛事最终成绩。专家评审、答辩等环节及其权重以赛事公告为准，本包不做约定。
>
> 附加题按 §8 单独计分，满分 10 分，**不计入 0–1 的客观分**，仅在客观总分并列时用于排序。合成规则：客观总分高者优先 → 客观总分相同则附加题得分高者优先。

1. **分层 NDCG（随机归一化，占 60%）**：按 `shop_main_cate` 分组，组内 NDCG@100（组不足 100 取全组），增益 `gain(S,A,B,C,D) = (15, 7, 3, 1, 0)`；各组**等权宏平均**（<20 品的组并入"其他"）。

   **每组先减掉"随机排序的期望值"再归一化**：

   ```
   NDCG_adj = (NDCG - E[NDCG_随机]) / (1 - E[NDCG_随机])
   ```

   `E[NDCG_随机]` 由该组的增益分布精确算出（逐位置线性期望，无近似）。含义：

   - **组内全同分 ≈ 0 分**（随机水平；同分按 `item_id` 兜底排序，实际得分会在 0 附近小幅波动）。打分全相同的提交拿不到任何白送的分；
   - **完美排序 = 1 分**；把 D 档排到前面导致 `NDCG_adj` 为负，按负分计；
   - 组内增益完全一致（例如整组都是 D）的组没有排序信息，**不参与宏平均**；
   - 同分时按 `item_id` 升序排（`item_id` 是随机编号，故同分 ≈ 随机）。

2. **冷启动子分（占 NDCG 部分的 20%）**：训练集里一条记录都没有的店铺（公开集 22.0% / 隐藏集 22.6%）单独成池，算一个整体的随机归一化 NDCG。**只靠老店历史先验的解法在这里拿不到分**——新店必须靠商品自身信号。

3. **决策得分（40%）**：看你在**单字段地板之上**的增量。损失表：

| 真实档 \ 决策 | 驳回 | 放行 |
|---|---|---|
| S | **12** | 0 |
| A | **8** | 0 |
| B | 2 | 2 |
| C | 0 | **3** |
| D | 0 | **4** |

   `L` 是代价表下的平均损失。**地板**由一条真实业务规律定义：`fulfillment_mode = 全托管` 的商品判"放行"，其余判"驳回"（该规律与属性完整度严格对应，单字段原始决策分已有 0.51–0.54，不应再作为免费得分）。

   ```
   决策得分 = max(0, (L_地板 - L_你的方案) / (L_地板 - L_全对))
   ```

   **锚点由该榜自己的标签档位分布现算**：

   - **地板 = 0.000 分**（照搬单字段规则不拿决策分）；
   - **全对 = 1.000 分**（逐品取放行/驳回中代价较小者；B 档两个选择代价都是 2，这 2 分无论如何都要付，所以"全对"的 L 不是 0）；
   - **低于地板记 0 分**，不会出现负的决策分；真正的增量按比例给 0–1 分。
   - 原始决策分 `(L_全放行 - L_你的方案) / (L_全放行 - L_全对)` **仍在控制台与评测 JSON 中输出**，只用于对照，不计入总分。

   （参考：公开 / 隐藏榜各 3,000 件上 L_全放行 = 2.300、L_全对 = 0.600、L_全驳回 = 2.400；B05 验证批为 2.222 / 0.592 / 2.599；单字段地板的 L 三榜约 1.38–1.41。这些数字都由档位分布决定，评分脚本会把你这一榜的锚点打印出来。）

四条命令都在**解压后的 `O1_爆品早知道_资料包/` 目录里**执行：

### 6.1 两个阶段：开发自测 vs 最终提交（不要混用）

| 阶段 | 训练数据 | 打分数据 | 绝对不能做 |
|---|---|---|---|
| **开发 / 自测** | `train_sub.csv`（B01–B04） | `val_items.csv` 当测试集，用 `val_truth.csv` 算分 | 把 `val_truth.csv` 的 `tier` 当作训练样本喂回模型（验证批只用于打分与选型，选型后用完整 `train.csv` 重训） |

最终阶段**不再生成也不再读取 `val_truth.csv`**：`predict.py` 只从 `--data-dir` 读 `train.csv`、`test.csv` 及其它随包文件，评分由组织者完成。

**参考分段（验证批 B05 4,321 件 / 公开 B06 3,000 件 / 隐藏 B07 3,000 件）**：

| 提交方案 | NDCG 部分（B05） | 决策分·原始（B05） | 决策增量·计分（B05） | 客观总分（B05） | 客观总分（公开） | 客观总分（隐藏） |
|---|---:|---:|---:|---:|---:|---:|
| 全部同分 + 全放行（什么都不做） | -0.013 | 0.000 | 0.000 | **-0.008** | **-0.004** | **+0.028** |
| `fulfillment_mode` 单字段地板（全托管放行，其余驳回；score 取 0/1） | +0.102 | +0.507 | 0.000 | **+0.062** | **+0.087** | **+0.103** |
| `baseline.py`（类目历史先验 + 代价阈值） | +0.037 | +0.360 | 0.000 | **+0.022** | **+0.035** | **+0.072** |
| `baseline_scores.csv` 的 LightGBM 分（仅排序，阈值没调） | +0.473 | -0.007 | 0.000 | **+0.284** | **+0.282** | **+0.258** |
| 完美答案（理论上限） | 1.000 | 1.000 | 1.000 | **1.000** | 1.000 | 1.000 |

> **怎么读这张表**：① 同分策略三榜都接近 0——`NDCG_adj` 减掉了随机底分，"交个常数"拿不到白送的分（个别榜出现 ±0.03 的小抖动，来自组内同分按 `item_id` 兜底排序，属正常）。② **单字段地板按定义记 0 分决策增量**：它的原始决策分 0.507（公开 0.526 / 隐藏 0.543）很可观，但这来自合作模式与属性完整度的强相关，是业务规律而非模型信号，所以不再计入总分；单字段的客观分只剩排序侧的 0.062 / 0.087 / 0.103。③ 决策侧只要做出**正的增量**，就说明修正了地板的误判；排序侧则要和"同组同分"比。④ 表中前四行方案在 B05 一列均按“`train_sub` 拟合、B05 报分”的批次外口径计算，**表里没有 in-sample 数字**；唯一例外是 `baseline_scores.csv` 那一行：该文件由全量训练集拟合（训练集拟合 AUC 0.814，公开集样本外 AUC 0.782），对 B05 属 in-sample，其 B05 一列偏乐观，公开 / 隐藏两列才是样本外的实测。

三个能直接读出来的结论：
① **随机/同分策略接近 0 分**——`NDCG_adj` 减掉了随机底分，"交个常数"不再有白送分；
② LightGBM 那套基线**排序强、决策弱**（`verdict` 极度保守，几乎全判驳回，低于地板），它的客观分全部来自排序侧——说明"排得准"和"阈值定得对"是两件独立的事；
③ **决策分的唯一来源是超过单字段地板**——照搬 `fulfillment_mode` 规则得 0；能修正它的误判才拿得到分。

## 7. 红线与 FAQ

**红线**

- **禁止时间穿越**：`shop_hist_monthly` / `category_trend.demand_index` 只能取 `batch ≤ 当前上架批次` 的行。**公开榜只收预测文件，无法自动核验**；终评代码由组织者**人工抽查** batch 过滤逻辑，违规成绩作废。
- **禁止从编号 / 行序里找信号**：`item_id`、`shop_id`、`supplier_id`、`cate_code` 都是随机重编码，行序也已打乱；基于行号或编号顺序的"特征"纯属噪音，写进模型只会掉分。
- **禁止使用平台审核/评级类分数**：`baseline_scores.csv` 是赛题**自制的公开练习基线**，不是平台机审分；真实机审类字段在脱敏时已整体剔除。
- **禁止获取隐藏测试集**：隐藏集不随任何渠道下发；任何试图从组织者环境、日志、缓存文件反推隐藏集数据或标签的行为，成绩作废。
- **不要试图"还原标题"**：真实池不含商品标题，文本信号就是 `attr_vals`；也没有图像。
- 验证集必须**按批次切分**（用过去预测未来），随机切分会高估效果。

**允许 / 禁止清单（消除歧义）**

| 操作 | 判定 |
|---|---|
| 用 `train.csv` 训练、调参、做特征选择 | ✅ 允许 |
| 用 `train.csv` 的 `tier` 按店铺 / 类目做目标编码 | ✅ 允许（只能用训练标签；建议 OOF / 平滑；不得使用 `val_truth` 或测试标签） |
| 用 `shop_hist_monthly` / `category_trend.demand_index` 中 `batch ≤ 当前上架批次` 的行 | ✅ 允许（这是本赛题给的历史信号） |
| 用 `test_public.csv` 的**无标签特征**做标准化 / PCA / 聚类 / 目标无关的特征工程 | ✅ 允许（但只能取 `batch ≤ 当前批次` 的行，且不得据此反推标签） |
| 用 `test_public.csv` 的类目频次、店铺商品数、`category_trend.supply_count` 等**本批次聚合统计**做特征 | ✅ 允许（本批次供给信息在上架当天可见） |
| 用**晚于当前批次**的 `shop_hist_monthly` / `category_trend.demand_index` 行 | ❌ 禁止（时间穿越） |
| 把 `val_truth.csv`（验证批真值）、`labels_*` 或由它们衍生的答案映射带进最终模型或代码包 | ❌ 禁止（本地验证阶段用完即弃；完整 `train.csv` 的标签可以正常训练，见上） |
| 用 `item_id` / `shop_id` 的编号大小、行号当特征 | ❌ 禁止（终评代码人工抽查；作为主特征则该维度无效） |
| 引入站外商品级数据、平台机审分、真实销量 | ❌ 禁止（附加题的站外宏观信息除外，见 §8） |
| 把公开集/隐藏集 ID 拿去外部检索、或试图反推隐藏集 | ❌ 禁止（成绩作废） |

> **自动检查范围**：格式 / 覆盖 / 值域 / 静态关键词由脚本检查；**时间穿越、编号/行序依赖不在自动扫描内，由组织者对终评代码人工抽查**。

**标签成熟期（必读）**：`tier` 的口径是**上架后第 2~8 天销量**分档。批次之间只隔 2 个自然日，所以"上一批商品的标签"在预测下一批时**理论上还没成熟**。本赛题的处理方式是：**由组织者统一按下架日结算标签，参赛者一律按 `batch ≤ 当前批次` 取历史特征即可，不需要、也无法自己处理成熟期**。所有队伍同一口径；但这意味着离线分数会略微偏乐观，属于本赛题的已知设定，不是数据错误。

**异常提交处理表**

本地 `evaluate.py` **默认先做严格校验**（UTF-8 编码 / 覆盖 / 唯一 / `score∈[0,1]` 且有限 / `decision` 合法），不通过直接退出；下表是加 `--allow-incomplete` 后与**正式评分器**一致的容错行为。终评 runner 同样先跑 `validate_submission.py`，**格式或编码不通过直接判 0，正式评分不会走容错分支**。

| 情况 | 处理 |
|---|---|
| 真值商品缺 `score` | `score` 记 -1.0，排到最后；`decision` 强制记「放行」并计入代价（即使该行写了「驳回」也不采用；**不使用真值兜底**） |
| `score` 非数值 / 为空 / NaN / inf | 视为缺失，同上 |
| 有 `score` 缺 `decision` | `decision = 放行 if score ≥ 0.5 else 驳回` |
| `decision` 不是「放行 / 驳回」 | 同上，按 `score ≥ 0.5` 推断 |
| 同一 `item_id` 出现多次 | **后一行完整覆盖前一行**：后一行 `score` 非法则视为缺失；后一行没写/写错 `decision` 则按最终 `score` 重新推断（不会沿用前一行）。`validate_submission.py` 会单独报重复 |
| 预测里多出真值以外的 `item_id` | 忽略，不参与排序与计分 |
| 预测文件为空 / item_id 全部不匹配 | **直接报错退出**（本地与正式评分器一致；不给 0 分兜底） |

> `validate_submission.py` 与本地默认严格模式的检查项一致：三列齐全、`score ∈ [0,1]` 且为有限数、`decision` 合法、无重复/缺失/多余行。正式评分器本身对缺失/非法值按上表容错，但**不建议**依赖容错——终评运行器会先跑格式校验，校验失败不进入评分。

| 问题 | 回答 |
|---|---|
| 公开测试集能拿来训练吗？ | 它没有标签，不能做监督训练；其**特征**可用于无监督/半监督或特征工程，但公开榜分数只反映公开集表现，不代表隐藏榜 |
| `baseline_scores.csv` 为什么不覆盖公开/隐藏集？ | 只下发训练集行——直接照抄官方基线分等于白送答案。你可以拿它做蒸馏目标或对照，但必须自己训练并泛化到没见过的批次。验证集、公开集和隐藏集都没有这一列，不能把它当输入特征；它由完整 `train.csv` 拟合，对 B05 属样本内（见 §6），本地验证时拿它做蒸馏可能偏乐观 |
| 客观分出现负数是正常的吗？ | 排序侧会：把 D 档排到前面，`NDCG_adj` 记负分。决策侧不再出负分——低于单字段地板一律记 0（原始决策分仍会打印，供对照） |
| 我怎么知道自己"有信号"？ | 对照 §6 参考分段（三榜实测）：同分 ≈ 0.000；单字段地板 0.062/0.087/0.103（原始决策分 0.507/0.526/0.543，计分为 0）；类目先验 0.022/0.035/0.072；练习基线分 0.284/0.282/0.258（B05/公开/隐藏）。决策侧有正的增量、排序侧明显高于同组同分，才算真的用上了商品自身信息 |
| 为什么公开榜只占 30%？ | 公开集时间更近、特征可见，仍可能被针对性调参；隐藏集时间更远、完全不可见，更能检验泛化，故权重更高（0.3 / 0.7 固定） |
| 公开榜每天都能提交吗？ | 截止前不限次数，以最后一次有效提交为准；组织者统一回分，没有每日回分 |
| 隐藏榜能提交几次？ | 代码包截止前可更新，以最后一次有效提交为准；截止前请在本地用验证批与公开测试集反复自测（组织者不提供试跑）；截止后**正式运行一次**（计分，失败不补跑） |
| 预测文件编码有什么要求？ | 必须 **UTF-8**（可带 BOM）。Excel 另存的 GBK/ANSI 会被 `validate_submission.py` / 评分器拒绝，并给出明确报错。表头 `item_id,score,decision` 大小写不敏感、忽略首尾空格 |
| 提交代码能用 GPU 吗？ | 不能，仅 CPU |
| 代码能联网下载模型吗？ | 不能，沙箱无网络；也不能安装其他依赖，只能用 §2.1 列出的库 |
| `score` 相同怎么排？ | 同分按 `item_id` 字典序升序，保证可复现（`item_id` 随机编号，故同分≈随机） |
| 预测缺行会怎样？ | 本地默认**直接报错**；加 `--allow-incomplete` 才按官方容错：缺 score 的行按 -1 排到最后、decision 强制记"放行"计入代价——**不会**用真实档位兜底。终评会先跑格式校验，缺行直接拒收，不建议留空 |
| 决策分能超过 1 吗？ | 不能，1 就是"全对"；最低为 0（单字段地板及以下记 0，见上方「客观分出现负数」一条） |
| 可以用外部数据吗？ | 主赛道不允许引入站外商品级数据；附加题允许站外宏观信息（见 §8 四条硬约束） |
| `listing_batch` 是月份吗？ | 不是。B01–B06 各覆盖真实 2 个自然日的上架量、B07 覆盖 3 个，**没有日历/季节含义**，别做月份特征 |
| `category_trend` 为什么只到 B06？ | 本包不含 B07 行：B07 的 `demand_index` 反映公开集（B06）当期动销，若拿来预测 B06 就是时间穿越。B07 行由组织者在终评沙箱内提供，代码需自己按 `batch <= 当前批次` 过滤 |
| `shop_hist_monthly` 的 B07 行为什么是空的/和 B06 一样？ | 店铺历史只结算到训练窗口 B05；沙箱里 B07 行等同 B06 行（都是 B05 末状态），公开集 B06 的动销不进入历史表。这是刻意设计，不是缺数据 |
| `score_band / onsale_band / follow_band` 是什么时点的？ | 均为**该商品上架当日**的店铺快照（严格按每品自己的上架日取当日分区）：店铺评分 / 在售规模 / 关注规模带，**不含上架后销量或评价**。同一店铺恒定是 band 化结果，别当时间序列 |
| `group_band` 在数据里吗？ | 不在。同款组表上架当日本品尚未入组，做不出当日口径；该字段与档位秩相关仅 0.057，同时 `is_similar` 在本批恒为 0，同款/重复铺货信息在本题不可用 |
| `fulfillment_mode` 和 `n_attr_rows` 为什么完全对应？ | 真实业务形态：全托管商品由平台代填属性（14,932 品全有属性），半托管/自运营由商家自填（4,224 + 3,844 全无属性）。不是泄漏；单靠它的原始决策分约 0.51–0.54，被定义为决策地板，记 0 分 |

## 8. 开放附加题（唯一一题，附加分上限 +10，用于并列名次区分）

### 附M · AI 选品助手 Copilot

> 为审核运营 / 买手造一个**能对话、能解释、能追溯来源**的选品助手：既读赛题包提供的数据，也**自主到站外检索市场信息**，帮一个真实的人在上架当天做出"放行还是驳回"的决定。

**要做出的四件事**

1. **分诊与解释**：给一件商品，说清"它为什么可能是爆品 / 为什么建议驳回"，解释必须落到具体字段与外部证据，不能是形容词；
2. **对话与追问**：接得住反问——"我认为这个品被误判，按【重复铺货】再看一遍""这个风格在目标市场最近有多热""这个店的评分我有疑虑"；
3. **例外闭环**：运营推翻建议时，留决策记录与理由，形成可审计的例外流程；
4. **域外检索**：主动到站外找证据（见下）。

**数据源：站内必用 + 站外开放**

站内（本包提供）：`baseline_scores`（分数 + top3 归因）、`audit_reason_dict`（12 类理由）、`human_review_sample`（含 40 条人机分歧）、主表与 `attr_vals`。

站外（**不限白名单，鼓励挖掘**）：搜索热度（Google Trends 等公开指数）、社媒趋势（TikTok / Pinterest / Reddit / 公开小红书笔记的**风格与场景热度**）、零售观察（公开榜单页、竞品官网品类结构）、与具体商品销量无关的通用商业节点、目标市场法规与认证要求、物流时效与汇率、公开商标/专利检索。

**四条硬约束（违反则该维度不计分）**

1. **禁止反查商品结果**：不得通过外部检索获取本赛题商品**上线后的真实销售/评价/榜单结果**——那是未来信息，等于偷看答案；允许的是"该风格 / 该场景 / 该类目"的宏观热度，并须注明信息时间点；
2. **宏观热度、不看结果**：外部信息只能是“风格 / 场景 / 类目”层面的宏观热度、趋势或规则，不得是本赛题具体商品的销量、评价或榜单结果。批次不对应公开日历，本题**不要求**与 `listing_batch` 做日历对齐；引用时须注明信息发生时间与抓取时间，并在证据链中说明该信息为何不属于“上架之后才可知”的内容；
3. **合规采集**：遵守 robots.txt 与目标站条款，不抓登录墙内容，不采集个人信息，不绕过反爬；
4. **可追溯**：每次外部检索记入证据链日志（query / 来源 / 抓取时间 / 引用片段 / 支撑了哪个结论）——**没有记录的外部信息等于不存在**。

**五件交付物**：① 可跑的 demo（Web/CLI 均可，评委 5 分钟内能自己走完一次判断）；② 一页产品说明；③ **检索证据链日志**（≥20 条真实交互，含 ≥5 条分歧被推翻的追问）；④ AI 使用与数据合规声明（模型/prompt 要点/成本/外部来源清单）；⑤ 过程记录（关键取舍 + 至少一个被证伪的假设）。

**评审：四维锚定（2/4/6）盲评 + 三评委取中位**

| 维度 | 分 | 6 分长这样 |
|---|---|---|
| 有用性 | 3 | 运营用一个判断就能开工；例外流程能接住"我觉得你错了" |
| 证据链 | 3 | 每条判断都能顺着日志回到原文；第三方能重跑出同样结论 |
| 域外数据运用 | 2 | 外部信息真正改变了某个判断，且说明"没有它会怎么判" |
| 诚实与工程 | 2 | 讲清失效场景、成本、幻觉抑制与被证伪的假设 |

**没有标准答案 ≠ 没有答案**：给不出证据的论述**单项封顶 40%**；客观数字（如基线分提升）降级为证据，不能代替论证；诚实的负结果 ≥ 粉饰的正结果。
